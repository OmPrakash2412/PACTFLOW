# PACTFLOW Database Schema & Migrations

## 1. Relational Entity Architecture
PACTFLOW utilizes PostgreSQL with Supabase Row Level Security (RLS) policies.

### Tables
1. **`profiles`**: User profiles with explicit roles (`client`, `freelancer`, `admin`) and PayPal email mappings.
2. **`projects`**: Top-level project entities with title, description, budget, and currency.
3. **`project_members`**: Membership link between profiles and projects with role boundaries.
4. **`agreements`**: Versioned technical agreements generated by Gemini Pact Architect or manually drafted.
5. **`agreement_acceptances`**: Dual-party digital signatures with cryptographic hash sealing.
6. **`milestones`**: Sequenced deliverables with financial allocations and acceptance criteria.
7. **`deliverables`**: Submitted code links, test logs, and live staging URLs.
8. **`verification_reports`**: Objective Gemini Evidence Inspector reports with honest classification and confidence estimates.
9. **`invoices`**: Authoritative PayPal Invoicing v2 records with invoice numbers and hosted payer URLs.
10. **`payments`**: Authoritative capture records with unique transaction IDs and webhook payloads.
11. **`paypal_webhook_events`**: Idempotent webhook receipt registry preventing replay attacks.
12. **`trust_events`**: Cryptographic hash chain blocks ($H_n$) recording every state mutation.

## 2. Row Level Security (RLS)
- Multi-tenant isolation: Users only see projects and agreements they belong to.
- Immutable Ledgers: SQL triggers explicitly reject `UPDATE` and `DELETE` queries on `trust_events` and `payments`.
